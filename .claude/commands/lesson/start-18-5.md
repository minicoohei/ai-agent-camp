## 🚀 Step 1: PRD・要求資料の読み込みと要件への変換方法説明

このステップでは、これまで作成したPRDと要求資料から、IPA形式の要件定義書へ変換するための方法論を学びます。

```json

    }
  ],
  "hint": "選択した経験度に応じて、説明のレベルを調整します。"
}
```

**Step 1 の説明:**

要件定義書は、「何を作るのか」を明確にする重要なドキュメントです。IPA形式は日本の公式基準で、以下の特徴があります：

1. **構造化された記述方法**
   - 機能要件と非機能要件を明確に分離
   - 各要件に一意のID（REQ-001など）を付与
   - トレーサビリティの確保

2. **PRDから要件への変換プロセス**
   ```text
   PRD（製品仕様）
   → ユーザーシナリオ抽出
   → 機能分解
   → 要件記述
   → レビュー＆確定
   ```

3. **IPA形式の主要セクション**
   - システム概要
   - 機能要件（画面別/ユースケース別）
   - 非機能要件（性能、セキュリティ、可用性など）
   - 制約条件・依存関係
   - 用語定義・前提条件

**期待される結果:**
- PRDの内容を理解し、要件要素を抽出できる
- IPA形式の構成が頭に入っている
- 次のステップ（機能要件の詳細化）に進む準備ができている

## 🚀 Step 2: 機能要件の詳細化

このステップでは、PRDに記載された機能を画面単位で展開し、各画面の入力・処理・出力・制約を定義します。

```json
    }

  "hint": "TaskFlowはUI中心のツールなので、画面単位がおすすめです。"

```

**Step 2 の詳細:**

**機能要件の記述フォーマット:**

```text
REQ-F-001: タスク作成画面
  説明: ユーザーが新規タスクを作成するための画面

  入力:
    - タスク名（テキスト、必須、最大100文字）
    - 優先度（ドロップダウン：高/中/低）
    - 期日（日付ピッカー、オプション）
    - 説明（テキストエリア、オプション、最大500文字）

  処理:
    - 入力値の妥当性チェック
    - タスクをDBに保存
    - タスクリスト画面へリダイレクト

  出力:
    - 保存成功メッセージ
    - 新規タスクをリストに追加

  制約:
    - ユーザーは認証済みである必要がある
    - 同じ名前のタスク複数作成は可能
```

**TaskFlow要件定義での主要機能（例）:**

1. **REQ-F-001: ワークスペース作成**
   - 入力：ワークスペース名、説明、メンバー設定
   - 処理：メンバー権限の初期化、初期タスク生成
   - 出力：ワークスペースリストに追加

2. **REQ-F-002: タスク作成**
   - 入力：タイトル、説明、優先度、期日、担当者
   - 処理：タスクID生成、ステータス初期化
   - 出力：タスク詳細画面に遷移

3. **REQ-F-003: タスクステータス更新**
   - 入力：タスクID、新ステータス
   - 処理：状態遷移ルールの検証、タイムスタンプ記録
   - 出力：更新確認メッセージ

4. **REQ-F-004: タスク検索・フィルタ**
   - 入力：キーワード、優先度、ステータス、担当者
   - 処理：複合条件での検索、ソート
   - 出力：マッチしたタスクリスト

5. **REQ-F-005: コメント追加**
   - 入力：タスクID、コメント本文
   - 処理：コメント保存、メンション通知
   - 出力：コメント表示エリアに追加

以下、同様に10個以上の機能を詳細化してください。

**期待される結果:**
- 最低10個以上の機能要件が定義されている
- 各機能に入力・処理・出力・制約が記載されている

| 項目 | 要件 | 根拠 |

| 項目 | 要件 | 根拠 |

| レスポンスタイム（API） | 200ms以内 | SLA 99.5%要件 |
| 同時接続数 | 1000+ | 成長段階での需要想定 |

**セキュリティ要件:**

| 項目 | 要件 | 実装方法 |

**トラブル別解決方法:**

### PRD/要件ファイルが見つからない

**原因:** 16-4 をスキップしたか、ファイルの保存場所が異なる

**確認コマンド:**
```bash
ls -la output/pm/
find . -name "prd.md"
find . -name "requirements-brief.md"
```

**解決方法:**
1. 16-4 に戻って、PRDを作成してください
2. ファイルが生成されたら、output/pm/ ディレクトリにコピーしてください
```bash
cp ~/prd.md output/pm/prd.md
```

### 機能が多すぎて整理できない

**原因:** PRDに記載された機能を全て要件に含めようとしている

**MoSCoWメソッドを使用:**
- **Must have（必須）:** MVP段階で必ず必要
- **Should have（推奨）:** 次のフェーズで実装
- **Could have（望ましい）:** さらに先のフェーズ
- **Won't have（不要）:** スコープ外

**対応:**
1. PRDの機能を3分類する
2. 要件定義書には Must have に限定（10-15個程度）
3. Should/Could は別ドキュメント（backlog.md）に記載

### 非機能要件の数値設定で迷っている

**一般的なベストプラクティス参考値:**

**スタートアップ向け:**
- レスポンスタイム：2〜3秒
- 同時接続：100〜500
- 稼働率：99%
- 多要素認証：オプション

**企業SaaS向け:**
- レスポンスタイム：1秒以内
- 同時接続：1000+
- 稼働率：99.5%
- 多要素認証：必須

**解決方法:**
1. ビジネスゴール（売上、ユーザー数予測）から逆算
2. 競合製品のSLAを参考にする
3. 不確実な場合は、後で改訂可能として「TBD」と記載

### requirements-spec.md生成エラー

**一般的なエラー:**

```text
Error: prd.md not found
```
→ ファイルパスを確認してください。フルパスで指定してください。

```text
Error: Invalid YAML header
```
→ requirements-brief.md のYAMLフロントマッターを確認してください。

**解決方法:**
```bash
# ファイル存在確認
test -f output/pm/prd.md && echo "OK" || echo "NOT FOUND"

# JSONバリデーション（YAML含む）
python3 -c "import yaml; yaml.safe_load(open('output/pm/requirements-brief.md'))"  # Windowsでは python3 を python に読み替え

# pm-toolkitのバージョン確認
pm-toolkit version
```

### トレーサビリティマトリクスが空白

**原因:** PRD と requirements-spec.md で要件ID の対応付けが未実施

**解決方法:**
1. PRDの各要件に ID を付ける（例：PR-001, PR-002）
2. requirements-spec.md で、各要件が PR-XXX を参照するよう記載
3. トレーサビリティマトリクスを手動で作成

**テンプレート:**

| PRD ID | PRD要件 | 要件定義ID | ステータス |
|--------|--------|---------|----------|
| PR-001 | ワークスペース管理 | REQ-F-001 | ✓ |
| PR-002 | タスク管理 | REQ-F-002〜REQ-F-005 | ✓ |
