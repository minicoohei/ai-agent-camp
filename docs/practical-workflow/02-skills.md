# 2. Skillsを別の入力へ再利用する

[演習一覧](README.md) → この演習 → [反復ループ](03-iteration.md)

目的は、毎回長い依頼を書き直さず、同じ品質条件で違う案件を確認することです。所要30分。[Module 6](../../courses/aiagent/lesson03-core/module06-agent-development/practice/exercise.md)のSkill作成を、実際の再利用へつなげます。

**一度うまく進んだ仕事の手順と、合格にした判断基準を残して、次の案件へ使います。** 最初の1件では計画や修正に時間をかけても、その確認方法をSkillへ戻せば、2件目から説明する内容を減らせます。短い依頼でも必要な確認が省かれていないことを確かめましょう。

このページから始める方は、先に[演習一覧の「開始前の準備」](README.md)を実施して `camp-practice` を作成してください。GitHub演習を終えていなくても進められます。

## 「手順」「入力」「成果物」を分ける（5分）

操作場所は `camp-practice` のエディタです。次の3つを開きます。

| ファイル | 役割 | 案件が変わったとき |
| --- | --- | --- |
| `skills/quote-review/SKILL.md` | いつ使うか、何を受け取り何を返すか | 同じまま使う |
| `skills/quote-review/playbook.md` | 読む順序、固定の計算ルール、品質基準 | 共通ルールの変更時だけ直す |
| `cases.json` | その案件の明細・提示額 | 今回の入力を選び直す |

Skillは手順のファイル、Commandは呼び出しの入口、Agentは担当する役割です。Skillを置いただけでは、実行された証拠にはなりません。この演習ではファイルのパスを明示し、AIが参照した版と入力IDを報告させます。

## 1件目を実行する（10分）

AIチャットに貼ります。

```text
skills/quote-review/SKILL.md と playbook.md を読み、cases.json の Q-001 を確認してください。
結果は evidence/review-Q-001.md に保存してください。
入力ID、参照したSkillのversion、合計の計算根拠、提示額との差、判定、未確認事項を書いてください。
不足データは推測せず「確認待ち」にしてください。入力ファイルの変更や外部送信はしません。
```

成功条件は、単に「問題なし」ではなく **小計55,000円、値引き後55,000円、税込60,500円、提示額との差0円** が明細から再計算できることです。税率10%は演習上の固定ルールで、実務の税務判断には使いません。

## 同じSkillを2件目へ使う（10分）

新しいチャットを同じフォルダで開くか、前の結果を参照しないように指定します。依頼文の入力IDを `Q-002`、保存先を `evidence/review-Q-002.md` に変更し、Skillの本文は変更せず実行します。

期待値は **小計100,000円、値引き後95,000円、税9,500円、税込104,500円**。提示額110,000円との差は **提示額−計算額=5,500円** です。判定は「要修正」。1件目の会社・金額を引き継いでいないことを確認してください。

2件の出力で見出しと判定基準が揃えば、案件入力を差し替えて手順を再利用できています。AIの文章が同一である必要はありません。数値と根拠が揃うことを確認します。

確認結果の末尾に「今回渡し直したもの」と「Skillから再利用したもの」を1行ずつ書きます。前者は案件IDと出力先、後者は計算ルール・照合手順・出力形式です。実務で適用条件が違うときは、その違いを先に確認し、同じ手順を使えるか判断します。

## 品質条件を1つ改善する（5分）

例えば出力に入力IDがないと、どの見積か照合できません。共通の改善は出力文だけでなく `playbook.md` に追記し、`SKILL.md` のversionを `1.0.1` に変更します。変更理由を `evidence/skill-change.md` に残し、2件とも再実行して改善を確認します。もともと条件を満たす場合は「差額の符号の意味を明記する」を追加して試します。

人が行うレビューを、次回にも使える言葉にします。「もう少し丁寧に」なら、例えば「差額がある場合は、どの明細と計算ルールを見て判断したかを書く」と具体化します。今回の出力を直すことと、次回も同じ観点で確認できるようにすることをセットで行います。

SkillはAIへ渡す手順です。毎回確実に検査したい計算やファイル形式は、テスト用スクリプトなどで確認する方法もあります。[GitHub演習](01-github.md)では、その検査をPR更新時に実行しています。手順を書く場所と、実行結果を確認する仕組みを分けて考えてください。

架空の会社名や金額をSkill本文へ固定しないでください。別案件へ再利用したときに前の情報が混入する原因になります。外部のSkillを使う場合も、同梱スクリプト・通信先・必要権限を読んでから利用します。

## つまずいたとき

| 症状 | 確認・再開する場所 |
| --- | --- |
| Skillが見つからない | 作業フォルダと相対パスを確認。自動検出の設定を増やす前にファイルを直接読ませる |
| 「できました」だけ返る | 出力ファイルと参照した入力ID・版を確認。実行不能なら未実行と記録 |
| 案件ごとに見出しが違う | 出力形式をplaybookで固定し、両方を再実行する |
| 金額が違う | `cases.json` の明細と演習ルールに戻る。AI同士の同意を正解の根拠にしない |
| 必須項目がない | 「確認待ち」として不足項目を残す。入力を勝手に埋めない |

- [ ] 2件で同じ手順・違う入力を使用した
- [ ] Q-001は一致、Q-002は5,500円の差を明細で確認した
- [ ] Skillの版と変更理由が残っている
- [ ] 2件目で省けた説明と、毎回確認すべき案件固有の条件を説明できる
- [ ] 実行できたことと、結果が正しいことを別々に確かめた
