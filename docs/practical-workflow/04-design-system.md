# 4. デザインシステムを作る

[演習一覧](README.md) / [Module 18の入口](../../courses/aiagent/lesson03-core/module18-pm-sysdef/practice/exercise.md)

色・文字・余白・部品・状態を共通のルールにして、AIへ渡せる形にする45分の演習です。デザインシステムは見た目のサンプル集だけでなく、「いつ、どの部品を、どの状態で使うか」の約束を含みます。

**「見やすくして」という要望を、AIに渡せて、できあがりと照合できる基準へ変えます。** 例えば「見積金額をすぐ見つけたい」なら、金額を置く場所、文字の強さ、画面幅が狭いときの表示を決めます。人が意図を決め、共通ルールと見本に残すことから始めます。

AIとターミナルの作業フォルダは `camp-practice` のままです。このページの依頼文のパスは、すべてこのフォルダを起点にします。編集対象は配下の `design/`、入力の `cases.json` は作業フォルダ直下です。`design/specimen.html` をファイルからブラウザで開けます。外部フォント、画像、サービス接続はありません。これは部品と状態の**静的見本**です。ボタンによる計算・送信・保存機能は実装していません。

このページから始める方は、先に[演習一覧の「開始前の準備」](README.md)を実施して `camp-practice` を作成してください。画面作成はGitHub演習の完了を待たずに進められます。

## 手順1：利用者と必要な画面を決める（5分）

架空の営業担当が、見積一覧を確認し、明細の金額を照合します。`design/decisions.md` に次を記載します。

```text
利用者：営業担当
目的：見積の提示額と計算額を照合する
画面：一覧、詳細
共通部品：見出し、カード、金額、状態ラベル、操作ボタン
状態：通常、空、処理中、失敗
対象外：顧客への送信、認証、実データ、決済
```

## 手順2：見た目の値に名前を付ける（10分）

`design/tokens.css` を開きます。トークンは「同じ意味に使う値へ名前を付けたもの」です。例えば `--color-primary` を変えると、同じ役割のボタンをまとめて変更できます。

| 分類 | 例 | 使い方 |
| --- | --- | --- |
| 色 | `--color-primary: #2457a7` | 主要操作。状態の区別は文言も併用 |
| 文字 | 本文16px、見出し24px、行間1.6 | 見出しの階層を揃える |
| 余白 | 8px、16px、24px | 部品内・部品間・大きな区切りで使い分ける |
| 形 | 角丸8px、枠線 | 同じ種類のカードを揃える |
| フォーカス | 輪郭線3px | キーボードで位置を見失わない |

青を「大きい売上」など別の意味に使わないよう、意味と使用場所を `decisions.md` に書きます。ブランドのロゴや既存顧客の画像はコピーしません。

値に加えて理由を1行残します。例えば「主要操作の色を揃え、次に押す場所を見つけやすくする」。あとでAIが画面を増やすときにも、どの場面で同じルールを使うか判断する材料になります。

## 手順3：共通部品と4状態を作る（10分）

AIに依頼します。

```text
design/tokens.css と design/specimen.html を読み、見積一覧と詳細に使う共通部品の仕様を
design/components.md に書いてください。部品名、役割、使うトークン、表示する情報を含めてください。
通常・空・処理中・失敗の4状態について、文言、できる操作、できない操作を表にしてください。
現状は静的見本なので、未実装の計算や送信を実装済みとは書かないでください。
```

期待する状態表：

| 状態 | 文言の例 | 実アプリで必要な動作 |
| --- | --- | --- |
| 通常 | 確認待ち・見積を見る | 明細を開く |
| 空 | 見積はまだありません | 新規作成への案内 |
| 処理中 | 計算中です | 二重実行を防止する |
| 失敗 | 計算できませんでした | 入力を保持して再試行できる |

色だけで状態を伝えず、文章を付けます。処理中を演出する画像だけでは、二重実行防止の機能を検証したことにはなりません。

## 手順4：ルールを使って画面を作り、まとめて変更する（10分）

まずAIに3ファイルを読ませ、作る画面・再利用する部品・確認する状態を短く説明してもらいます。認識が合っていることを確かめてから、次を依頼します。

```text
design/decisions.md、design/components.md、design/tokens.css に従い、架空の見積一覧と詳細の
静的プロトタイプを design/prototype.html に作成してください。
cases.json の2件だけを使用し、全て架空であることを明記してください。
design/tokens.css を共通参照し、カードや状態ラベルは共通CSSクラスを使ってください。
4状態を確認できる見本を並べ、未実装の操作はそう表示してください。外部通信は不要です。
```

表示を確認したら、`tokens.css` の主要色を `#2457a7` から `#174b45` に1か所だけ変更します。`specimen.html` と新しい `prototype.html` の両方で、同じ役割の部品が更新されたか確認します。反映されない場合は、個別の色の直書きやCSSの参照漏れを調べます。

Figmaを使う発展演習では、自分が編集できる新規ファイルに色・文字・余白の定義、再利用部品、4状態、一覧・詳細の画面を作ります。実際のフレームURLと閲覧権限、参照版を `decisions.md` に記録し、AIへ渡します。URLがない場合に推測したURLを書かず、このファイル演習の成果とFigma未実施を分けて記録します。

## 手順5：見た目と機能を分けて検査する（10分）

ウィンドウの表示幅を390pxと1280pxにして、同じ状態で比較します。開発者ツールが使えなければ、講師が幅を設定し、受講者は値と結果を記録します。`evidence/design-check.md` に画面・幅・状態・観測値・合否・修正箇所を残してください。

| 検査 | 合格条件 |
| --- | --- |
| 見た目 | 横方向にはみ出さない、文字切れ0件、4状態を文章で判別できる |
| 共通化 | 両画面が同じtokens.cssを参照し、色の1回の変更が両方に反映される |
| 操作の見え方 | Tabキーで操作対象の位置が分かる。無効な操作と未実装を区別できる |
| 計算機能 | `camp-practice` で `python3 checks.py`（Windowsは `py -3 checks.py`）を実行し、見た目と別に実測結果を記録する |
| 保存・送信機能 | この静的演習では未実装。画面だけで成功と判定しない |

初期の `quote.py` をまだ修正していない場合、計算テストは4件中2失敗になります。その結果をそのまま記録し、計算の修正は[GitHub演習の手順2](01-github.md)で行います。デザインの合格と計算の未完了を混同しないでください。

表示崩れがあれば、幅・状態・どの要素かを特定してAIへ渡します。[反復ループ](03-iteration.md)と同じく、修正と再確認は最大3回、10分で止めます。未達の条件もそのまま提出します。

例えば「390pxの一覧で金額が切れる。金額全体が読めるように直し、1280pxでも確認して」と伝えます。個別の画面だけの問題か、共通部品の問題かを分け、共通ルールを変えた場合は一覧・詳細の両方を再確認してください。

- [ ] 色・文字・余白のルールをファイルにした
- [ ] そのルールを選んだ理由と、見本に対する修正箇所を説明できる
- [ ] 同じ部品を一覧と詳細で再利用した
- [ ] 通常・空・処理中・失敗の4状態がある
- [ ] トークン1か所の変更が両画面へ反映された
- [ ] 390px／1280pxの確認と未実装機能を記録した
